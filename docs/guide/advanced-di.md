# Advanced Dependency Injection

This guide covers patterns beyond basic field injection: Wire mode, interface injection, slice collection, lazy loading, prototype scope, and value injection.

## Wire mode (compile-time DI)

### Why Wire mode?

The default `ReflectResolver` uses Go reflection at runtime. It works well for most apps but has a cost: type lookups and field-population happen at process start. For apps with hundreds of components or strict startup-time budgets, **Wire mode** generates the wiring code at build time — zero reflection at runtime.

### How it works

1. Write your components normally (same markers, same `inject:"true"` tags)
2. Run `helix generate wire`
3. Helix generates a `wire_gen.go` file that calls `RegisterWireSetup`
4. At runtime, the `WireResolver` delegates to this generated function

```bash
helix generate wire
```

Generated output (`wire_gen.go`):

```go
// Code generated by helix generate wire. DO NOT EDIT.
package main

import (
    helix "github.com/enokdev/helix"
    "github.com/enokdev/helix/core"
    "your-app/user"
    "your-app/order"
)

func init() {
    helix.RegisterWireSetup(func(c *core.Container) error {
        userRepo := &user.Repository{}
        userSvc := &user.Service{Repo: userRepo}
        userCtrl := &user.Controller{Svc: userSvc}

        c.Register(userRepo)
        c.Register(userSvc)
        c.Register(userCtrl)
        return nil
    })
}
```

### Switch to Wire mode

```go
container := core.NewContainer(
    core.WithResolver(core.NewWireResolver()),
)
```

Or via `helix.App`:

```go
helix.Run(helix.App{
    Mode: helix.ModeWire,
    // no need to list Components — wire_gen.go registers them
})
```

### When to use Wire mode

| Situation | Use |
|-----------|-----|
| < 50 components | ReflectResolver (default) |
| > 100 components or startup time matters | Wire mode |
| CI/CD that can run `helix generate` | Wire mode |
| Embedding into a larger system | Wire mode |

## Interface injection

### One interface, one implementation

This is the common case. Register a concrete type that implements the interface, and inject by interface type:

```go
type EmailSender interface {
    Send(to, subject, body string) error
}

type SMTPEmailSender struct {
    helix.Service
    host string
}

func (s *SMTPEmailSender) Send(to, subject, body string) error { ... }

// Registration:
container.Register(&SMTPEmailSender{host: "smtp.example.com"})

// Injection by interface:
type UserService struct {
    helix.Service
    Email EmailSender `inject:"true"` // resolved to *SMTPEmailSender
}
```

### One interface, multiple implementations

Use `ComponentRegistration.ResolveAs` to control which interfaces a component satisfies:

```go
type NotificationSender interface {
    Send(to, message string) error
}

type SMSSender struct{ helix.Service }
type SlackSender struct{ helix.Service }
type EmailNotificationSender struct{ helix.Service }

container.Register(core.ComponentRegistration{
    Component: &SMSSender{},
    ResolveAs: []reflect.Type{reflect.TypeOf((*NotificationSender)(nil)).Elem()},
})
container.Register(core.ComponentRegistration{
    Component: &SlackSender{},
    ResolveAs: []reflect.Type{reflect.TypeOf((*NotificationSender)(nil)).Elem()},
})
container.Register(core.ComponentRegistration{
    Component: &EmailNotificationSender{},
    ResolveAs: []reflect.Type{reflect.TypeOf((*NotificationSender)(nil)).Elem()},
})
```

### Collecting all implementations (`collect`)

Use the `collect:""` tag to inject **all registered components** that satisfy an interface as a slice:

```go
type AlertService struct {
    helix.Service
    Senders []NotificationSender `collect:""`  // receives [*SMSSender, *SlackSender, *EmailNotificationSender]
}

func (a *AlertService) Alert(message string) {
    for _, s := range a.Senders {
        if err := s.Send("ops-team", message); err != nil {
            slog.Error("alert failed", "sender", fmt.Sprintf("%T", s), "err", err)
        }
    }
}
```

`collect:""` is particularly useful for plugin-style architectures: health indicators, event listeners, middleware, exporters.

### Excluding a component from an interface

Use `ExcludeFrom` to prevent a component from satisfying an interface it would normally match:

```go
container.Register(core.ComponentRegistration{
    Component:   &InternalEmailSender{},
    ExcludeFrom: []reflect.Type{reflect.TypeOf((*NotificationSender)(nil)).Elem()},
})
// InternalEmailSender won't appear in []NotificationSender slices
```

## Scope: Singleton vs Prototype

### Singleton (default)

One instance per container — shared by all components that request it. This is the right choice for stateless services, repositories, and connections.

```go
container.Register(&UserService{})  // singleton by default
```

### Prototype

A **new instance** is created each time the component is resolved. Use this for stateful, per-request, or short-lived objects.

```go
container.Register(core.ComponentRegistration{
    Component: &QueryBuilder{},
    Scope:     core.ScopePrototype,
})

// Each Resolve creates a fresh *QueryBuilder:
var qb1 *QueryBuilder
container.Resolve(&qb1)

var qb2 *QueryBuilder
container.Resolve(&qb2)

// qb1 != qb2
```

Practical use cases:
- Per-request query builders
- Stateful parsers / decoders
- Rate limiter instances per tenant

## Lazy initialization

A lazy component is not resolved until it is first accessed. Useful for expensive resources that may not be needed in every execution path:

```go
container.Register(core.ComponentRegistration{
    Component: &ReportGenerator{},
    Lazy:      true,
})

type AdminService struct {
    helix.Service
    Reports *ReportGenerator `inject:"true"` // not resolved at startup
}

// *ReportGenerator is only created when AdminService.Reports is first used
```

Lazy components still participate in the lifecycle (`OnStart` / `OnStop`) — but `OnStart` is called at first access, not at container startup.

## Value injection

Inject scalar configuration values directly into struct fields using the `value:""` tag:

```go
type SMTPService struct {
    helix.Service
    Host     string `value:"email.smtp.host"`
    Port     int    `value:"email.smtp.port"`
    Username string `value:"email.smtp.username"`
}
```

Wire the lookup function when creating the container:

```go
loader := config.NewLoader(...)

container := core.NewContainer(
    core.WithValueLookup(func(key string) (any, bool) {
        return loader.Lookup(key)
    }),
)
```

When using `helix.Run`, the config loader is wired automatically — `value:""` tags work out of the box.

Config file:

```yaml
email:
  smtp:
    host: "smtp.example.com"
    port: 587
    username: "noreply@example.com"
```

### Type coercion

The value lookup must return the right Go type. When using the Helix config loader, numeric and boolean values are returned as their native types if the YAML is typed correctly:

```yaml
smtp:
  port: 587       # → int
  tls: true       # → bool
  timeout: 10s    # → string (parse manually as time.Duration)
```

## Resolving all components of a type

`core.ResolveAll[T]` returns every registered component that implements `T`:

```go
// Resolve all HealthIndicator implementations:
indicators, err := core.ResolveAll[observability.HealthIndicator](container)
if err != nil {
    log.Fatal(err)
}

checker := observability.NewCompositeHealthChecker(indicators...)
```

This is how the observability starter discovers health indicators — and how the scheduling starter discovers `ScheduledJobProvider` implementations.

## Package scanning (`helix.App.Scan`)

Instead of listing every component explicitly, declare which packages to scan:

```go
helix.Run(helix.App{
    Scan: []string{
        "your-app/user",
        "your-app/order",
        "your-app/billing",
    },
})
```

Helix uses AST analysis to find all exported types that embed `helix.Service`, `helix.Controller`, `helix.Repository`, or `helix.Component`, then registers them automatically.

Combine with explicit `Components` for types that need constructor arguments:

```go
helix.Run(helix.App{
    Scan: []string{"your-app/..."},  // auto-discover all packages
    Components: []any{
        user.NewRepository(db),     // needs db argument
    },
})
```

## Dependency graph inspection

Inspect the resolved graph for debugging or tooling:

```go
container.Register(&UserService{})
container.Register(&OrderService{})
container.Register(&UserRepository{})

graph := container.Graph()
// graph.Nodes — list of component type names
// graph.Edges — map[string][]string of "component → its dependencies"

for node, deps := range graph.Edges {
    fmt.Printf("%s depends on: %v\n", node, deps)
}
// UserService depends on: [*UserRepository]
// OrderService depends on: [*UserService, *UserRepository]
```

## Common errors

| Error | Cause | Fix |
|-------|-------|-----|
| `core.ErrNotFound` | No registered component matches the type | Register the missing component |
| `core.ErrCyclicDep` | A → B → A dependency cycle | Introduce an interface or restructure |
| `core.ErrUnresolvable` | Component can be found but cannot be constructed | Check field tags, nil pointers |
| `core.ErrShutdownTimeout` | An `OnStop` exceeded the budget | Increase `ShutdownTimeout` or fix the blocking code |

### Inspecting a cyclic dependency error

```go
if errors.Is(err, core.ErrCyclicDep) {
    var cyclic *core.CyclicDepError
    errors.As(err, &cyclic)
    fmt.Println("cycle:", strings.Join(cyclic.Path, " → "))
    // e.g.: "cycle: *UserService → *OrderService → *UserService"
}
```
